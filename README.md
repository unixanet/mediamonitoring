# mediamonitoring.am

Платформа медиамониторинга Армении. Клиенты: госструктуры, бизнес, посольства, международные миссии. Покрытие около 99.9% армянских медиа, архив с 2002 года. Каналы: онлайн-новости, Telegram, Facebook, YouTube.

Стек: PHP 8.1+ / MySQL, Tailwind CSS, Manticore Search, Grok API (xAI), оплата через Inecobank (Ineco eCom REST API).

Этот README описывает текущее состояние системы, накопленные проблемы и план апгрейда: собственный RSS-сборщик, новая БД и алерты через Manticore.

---

## Жёсткие правила работы с проектом

- Армянский текст копировать байт-в-байт. Никаких правок и никакой транслитерации.
- Менять только то, что просили. Без scope creep, только точечные правки.
- Файлы отдавать целиком, без обрезки.
- Не называть файлы кириллицей и спецсимволами.
- Сначала обсуждение и понимание задачи, потом код.
- Одна страница или компонент за раз: показать, получить фидбек, идти дальше.
- Эталон качества поиска по армянскому: поиск по подстроке (`LIKE '%слово%'`). MySQL FULLTEXT / `MATCH AGAINST` для армянского заметно ухудшает выдачу и не используется.

## 1. Manticore Search

### Доступ

- Логина и пароля у Manticore нет: приложение подключается по `mysqli` с пустыми пользователем и паролем на `65.75.203.244:9306`.
- Защита только сетевая: в `ufw` порт 9306 открыт исключительно для `207.180.203.115`. Снаружи порт недоступен.
- В конфиге порт 9306 слушает `0.0.0.0` (`mysql`), а `9308` (HTTP) и `9312` слушают только `127.0.0.1`.
- Пароли баз-источников (WordPress) здесь не продублированы, они лежат в `sync.php` и конфигурационных частях PHP-файлов на сервере.

### Как это работает

Manticore служит единым полнотекстовым индексом по четырём WordPress-источникам. Раньше поиск шёл LIKE-запросами прямо в MySQL.

Единая таблица `articles` создана с `min_infix_len='3'`:

| Поле | Тип |
|---|---|
| `title` | TEXT |
| `content` | TEXT (HTML очищается перед индексацией: `strip_tags` + схлопывание пробелов) |
| `post_date` | TIMESTAMP |
| `url` | STRING |
| `source` | STRING |

Запросы идут как `MATCH('*слово*')`: инфиксный индекс воспроизводит поиск по подстроке, как LIKE. Поле можно ограничить через `@title`.

Источники (WordPress-структура, таблицы `wp_posts` и `wp_postmeta`):

| Источник | Сервер | Множитель ID |
|---|---|---|
| media | `207.180.236.4` | 1 |
| pulse | `158.69.208.128` | 2 |
| julbaz | `130.254.47.26` | 3 |
| balance2 | `199.85.8.120` | 4 |

- **ID.** `множитель × 10 000 000 000 + исходный ID поста`, чтобы ID разных источников не пересекались.
- **Полный реиндекс:** `index.php`, запускается вручную. При первой индексации залито 583 004 статьи.
- **Инкрементальный синк:** `sync.php` каждые 2 минуты через cron. Чекпоинты по источникам в `checkpoints.json` (по `post_modified`). `BATCH_SIZE = 1000`, защита lock-файлом, ротация логов 3 дня.
- **Служебные таблицы Manticore:** `sync_runs` (история прогонов синка) и `search_log` (лог поисков). Старше 90 дней записи удаляются.
- **Дашборд синка:** `manticore_status.php`, защищён секретным ключом в URL (`$SECRET_KEY`). Показывает число документов, размер индекса, последний синк, рост индекса, последние поиски.
- **Telegram и Facebook** в Manticore не переехали, поиск по ним идёт прямыми LIKE-запросами (БД `telegram_med` и `facebook_med` на `194.238.28.184`).
- **Локальная БД** (localhost): пользователи, планы, ключевые слова, кэш трендов.

### Правила и грабли Manticore

- Без `LIMIT` отдаётся только 20 строк.
- `max_matches` по умолчанию 1000. Во всех запросах, которые тянут строки, добавлять `OPTION max_matches=N`.
- `COUNT(*)` точен независимо от `max_matches`.
- Условие `AND field != ''` на TEXT-полях молча даёт ноль результатов. Так не писать.
- Очищать таблицы только через `TRUNCATE TABLE`, а не `DELETE FROM` без `WHERE`.
- Ключевые слова перед оборачиванием в `'*слово*'` обязательно прогонять через `escapeMatchQuery()`.
- Из-за `min_infix_len='3'` слова короче трёх символов в инфиксном режиме не ищутся.

## 2. Проблемы, с которыми мы столкнулись

### Нагрузка и скорость поиска
- `LIKE '%слово%'` в MySQL делает полный перебор таблицы и не зависит от индексов. На WordPress-базах с сотнями тысяч статей это медленно, а для частотных слов с тысячами результатов тем более.
- Сервер media держал около 300–363% CPU. Нашли и убрали дублирующий FULLTEXT-индекс и плагин WordPress, запускавший `CHECK TABLE` по 15 таблицам одновременно. Нагрузка упала, но тест LIKE на media оставался около 7,9 с против 4,7 с на pulse при сопоставимом числе строк. Вероятные причины: размер `post_content` и фрагментация таблиц.
- До миграции поиск ограничивали последними 60 днями, а более старое отправляли в отдельный архив (`archive.php`).
- Социальные источники до сих пор на LIKE и остаются узким местом при росте нагрузки.
- Тренды: пока фразу за фразой ходили в БД, страница не справлялась. Решение: n-граммы в памяти по источникам. Тренды считаются кроном раз в 3 часа в двух таблицах (`trends_cache` и `trends_articles`), страница читает только локальную БД. Остаётся последний двухчасовой батч.
- Экспорт PDF не должен вызывать Grok синхронно, иначе сервер подвисает. Данные приходят POST-ом с фронтенда.
- Идёт исследование фрагментации таблиц (`OPTIMIZE TABLE`) и сравнение среднего размера контента в базах media и pulse.

### Качество поиска по армянскому
- FULLTEXT / `MATCH AGAINST` в MySQL для армянского даёт заметно худшую выдачу, поэтому подстрочный поиск (LIKE) остаётся эталоном качества.
- Подстрока естественно покрывает падежные формы и суффиксы армянских слов, чего не делает словный FULLTEXT.
- Задача апгрейда: сохранить точность подстрочного поиска, но убрать полный перебор. Manticore с инфиксным индексом решает это для основного поиска, а теперь та же логика нужна для алертов (раздел 4).

### Прочее
- После рестарта сервера PHP 8.1+ с режимом mysqli `MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT` вскрыл скрытые баги. Старым скриптам, рассчитывающим на возврат `false`, нужен `mysqli_report(MYSQLI_REPORT_OFF)` в начале.
- Известная проблема трендов: у фигур с очень высокой частотой упоминаний (например, Пашинян) базовая линия такая же высокая, поэтому они не всплывают в трендах.
- Оплата Media Digest: рекуррентные параметры не добавлены, пока не подтверждено, нужно ли автопродление.

## 3. Апгрейд: собственный RSS-сборщик и новая БД

### Цель
Вместо синка из четырёх WordPress-баз собирать данные самим: интерфейс, который тянет RSS-потоки всех источников (около 150) каждые пару минут и складывает их в одну новую БД с новой структурой. Manticore потом индексирует уже эту БД, а не WordPress-источники.

### Как это должно работать

**Сборщик.**
- Один постоянный процесс (systemd или supervisor), а не cron раз в минуту: нет наложений запусков.
- Параллельный опрос через `curl_multi`, 10–20 одновременных соединений. Все 150 фидов за 5–15 секунд.
- Условные запросы: хранить `ETag` и `Last-Modified` по каждому фиду. Большинство ответов будет 304 без тела.
- У каждого фида свой `next_check_at`. Активные источники опрашиваются раз в 1–2 минуты, вялые раз в 10–15 минут, интервал подстраивается под реальную частоту публикаций.
- Таймаут 10–15 секунд, экспоненциальный backoff по конкретному фиду. Один медленный источник никого не блокирует.
- Нагрузка: около 1,25 запроса в секунду, хватит 2 vCPU и 4 GB RAM, можно на существующем сервере.

**Админка (дашборд).**
- Управление списком источников: добавить, отключить, настроить интервал.
- Таблица здоровья фидов: последний успех, последняя ошибка, число подряд идущих ошибок, HTTP-код, время ответа. Нужна, чтобы молча умерший источник был виден сразу.
- Счётчики поступления статей по источникам за час и сутки, лента последних статей.
- Отдельный тип источника (`rss`, `html`, `social`) на случай сайтов без RSS: для них потребуется собственный парсер.

**Полный текст.**
- Если в RSS только анонс, полный текст добираем отдельной очередью (отдельный воркер), чтобы не тормозить опрос фидов. Это самая нагруженная и самая хрупкая часть системы, потому что вёрстка у каждого сайта своя.
- HTML очищаем при добавлении в БД (`strip_tags`, схлопывание пробелов), как это уже делает `sync.php`, чтобы мусор виджетов и скриптов не попадал в индекс.

**Новая БД (идея структуры).**
- `sources`: настройки фида и состояние опроса.
- `articles`: канонический URL, заголовок, текст, дата публикации в UTC, `source_id`, хеш для дедупликации, сырой RSS-элемент для возможности перепарсить.
- Дедупликация по `guid`, а если его нет или он нестабилен, по хешу нормализованного URL без UTM-меток.
- Правки статей после публикации: решить, перезаписываем или версионируем.
- Кодировка `utf8mb4` везде, чтобы армянский текст не искажался.
- Собственные ID через автоинкремент и `source_id` вместо схемы со смещениями `10B`.
- MySQL остаётся источником истины. Manticore строится как real-time индекс над этой БД с теми же настройками инфиксного индекса (`min_infix_len='3'`).

**Миграция.**
- Архив с 2002 года остаётся в старых базах. Нужно решить, переносить ли его в новую структуру или держать рядом.
- Старый индекс Manticore работает параллельно, пока новый не докажет, что он не хуже.

## 4. Алерты клиентам без LIKE

### Как сейчас
Рассылка (email и Telegram) опирается на LIKE-запросы по ключевым словам клиента. По качеству для армянского это эталон, но дорого по нагрузке: каждый запрос перебирает таблицы. Цель: убрать нагрузку и не потерять ни одного совпадения, которое находит LIKE.

### Принцип
Manticore с инфиксным индексом (`*слово*`) уже воспроизводит подстрочный поиск. Значит, критерий успеха простой: новая система находит всё, что находил LIKE (ни одного пропуска), а лишнее при необходимости отсекается проверкой.

### Два варианта реализации

**Вариант A: простой, опрос Manticore по новым статьям.**
- Раз в 1–2 минуты для каждого ключевого слова клиента запрос к Manticore с условием «только статьи новее последней обработанной» (по ID или `post_date`).
- На инфиксном индексе это быстрые запросы, полный перебор исчезает.
- Минус: число запросов растёт с числом ключевых слов у всех клиентов.

**Вариант B: percolate (обратный поиск), масштабируемый.**
- Запросы клиентов хранятся как правила в percolate-таблице Manticore.
- Каждая новая статья один раз прогоняется через эту таблицу, Manticore возвращает сработавшие правила.
- Нагрузка пропорциональна числу новых статей, а не числу клиентов. Лучше при росте базы клиентов.
- Требует проверки, что percolate-таблица поддерживает те же инфиксные подстановки, что основной индекс.

Рекомендация: начать с варианта A (меньше риска, использует уже работающий механизм), перейти на B, если нагрузка от опроса начнёт расти.

### Как гарантировать качество
1. **Одинаковые настройки индекса** для основного поиска и для алертов (`min_infix_len='3'`, одинаковая обработка регистра и символов).
2. **Теневой режим 1–2 недели.** Старая LIKE-логика и новая работают параллельно, результаты сравниваются. Фиксируем: что новая пропустила (потеря охвата, недопустимо) и что добавила (новые находки или шум). Переключаем клиентов, только когда пропусков нет.
3. **Проверка кандидатов в PHP** (при необходимости): Manticore даёт кандидатов, PHP подтверждает совпадение по подстроке без учёта регистра так же, как LIKE. Это защита от расхождений токенизации.
4. **Сверх LIKE:** ранжирование по релевантности, дедупликация одной новости из нескольких источников в одно уведомление, группировка в дайджест вместо потока писем.

### Доставка
- Сработавшие совпадения попадают в таблицу очереди отправки: клиент, статья, канал (email или Telegram), статус, число попыток.
- Отдельный воркер отправляет сообщения с повторами и логом ошибок. Сборщик RSS и отправка независимы.
- Защита от дублей: уникальная пара «клиент, статья». Одну статью клиент не получит дважды.
- Ограничение частоты по клиенту, чтобы всплеск новостей не превращался в сотни писем.

### Что нужно проверить до внедрения
- Многословные ключевые слова: LIKE ищет подстроку через пробел, а токенный индекс работает по словам. Нужно убедиться, что фраза находится так же.
- Ключевые слова короче трёх символов (из-за `min_infix_len='3'`).
- Поведение с дефисами, кавычками и другой пунктуацией внутри армянского текста.
- Приведение регистра армянских букв.
- Пропускная способность при пиковой нагрузке и числе активных правил.
