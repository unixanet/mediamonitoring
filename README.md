# mediamonitoring.am

Платформа медиамониторинга Армении. Клиенты: госструктуры, бизнес, посольства, международные миссии. Покрытие около 99.9% армянских медиа, архив с 2002 года. Каналы: онлайн-новости, Telegram, Facebook, YouTube.

Стек: PHP 8.1+ / MySQL, Tailwind CSS, Manticore Search, Grok API (xAI), оплата через Inecobank (Ineco eCom REST API).

Этот README описывает текущее состояние системы, накопленные проблемы и план апгрейда: собственный RSS-сборщик, новая БД и алерты через Manticore.

### Как это работает

Manticore служит единым полнотекстовым индексом по четырём WordPress-источникам. Раньше поиск шёл медленными LIKE-запросами прямо в MySQL.

Источники (WordPress-структура, таблицы `wp_posts` и `wp_postmeta`):

| Источник | Сервер |
|---|---|
| media | `207.180.236.4` |
| pulse | `158.69.208.128` |
| julbaz | `130.254.47.26` |
| balance2 | `199.85.8.120` |

- **ID.** Чтобы ID разных источников не пересекались, используется смещение: `(номер источника, 1–4) × 10 000 000 000 + исходный ID поста`.
- **Полный реиндекс:** `index.php`.
- **Инкрементальный синк:** `sync.php` каждые 2 минуты. Для каждого источника хранится свой чекпоинт. `BATCH_SIZE = 1000`, защита lock-файлом, ротация логов 3 дня.
- **Дашборд синка:** `manticore_status.php`.
- **Локальная БД** (localhost): пользователи, кэш трендов и прочее.
- **Telegram и Facebook** в Manticore не переехали, поиск по ним идёт прямыми LIKE-запросами.

### Правила и грабли Manticore

- Без `LIMIT` отдаётся только 20 строк.
- `max_matches` по умолчанию 1000. Во всех запросах, которые тянут строки, добавлять `OPTION max_matches=N`.
- `COUNT(*)` точен независимо от `max_matches`.
- Условие `AND field != ''` на TEXT-полях молча даёт ноль результатов. Так не писать.
- Очищать таблицы только через `TRUNCATE TABLE`, а не `DELETE FROM` без `WHERE`.
- Ключевые слова перед оборачиванием в `'*keyword*'` обязательно прогонять через `escapeMatchQuery()`.

## 2. Проблемы, с которыми мы столкнулись

### Нагрузка и скорость поиска
- LIKE-запросы по большим WordPress-таблицам были слишком медленными. Это стало причиной перехода на Manticore.
- Социальные источники до сих пор на LIKE и остаются узким местом при росте нагрузки.
- Тренды: пока фраза за фразой ходили в БД, страница не справлялась. Решение: строить n-граммы в памяти по источникам. Тренды теперь считаются кроном раз в 3 часа в двух таблицах (`trends_cache` и `trends_articles`), страница читает только локальную БД. Старые данные удаляются, остаётся последний двухчасовой батч.
- Экспорт PDF не должен вызывать Grok синхронно, иначе сервер подвисает. Данные приходят POST-ом с фронтенда.
- Идёт исследование фрагментации таблиц (`OPTIMIZE TABLE`) и сравнение среднего размера контента в базах media и pulse.

### Точность LIKE для армянского языка
LIKE ищет подстроку, поэтому:
- **нет границ слов**: ключевое слово находится внутри других слов (ложные срабатывания);
- **нет морфологии**: армянские падежи и суффиксы дают разные формы одного слова, точная подстрока их не покрывает, а широкая даёт шум;
- **нет нормализации**: регистр и варианты написания обрабатываются только тем, как настроена коллация.

Раньше мы осознанно оставили LIKE, потому что стандартный FULLTEXT/MATCH AGAINST в MySQL давал для армянского худшее качество. Задача апгрейда не в том, чтобы вернуться к FULLTEXT, а в том, чтобы получить поиск лучше LIKE через правильно настроенный индекс Manticore плюс проверку результата (см. раздел 4).

### Прочее
- После рестарта сервера PHP 8.1+ с режимом mysqli `MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT` вскрыл скрытые баги. Старым скриптам, рассчитывающим на возврат `false`, нужен `mysqli_report(MYSQLI_REPORT_OFF)` в начале.
- Известная проблема трендов: у фигур с очень высокой частотой упоминаний (например, Пашинян) базовая линия такая же высокая, поэтому они не всплывают в трендах.
- Оплата Media Digest: рекуррентные параметры для подписки Media Digest не добавлены, пока не подтверждено, автопродление нужно или нет.

## 3. Апгрейд: собственный RSS-сборщик и новая БД

### Цель
Вместо синка из четырёх WordPress-баз собирать данные самим: интерфейс, который тянет RSS-потоки всех источников (около 150) каждые пару минут и складывает их в одну новую БД с новой структурой. Manticore потом индексирует уже эту БД, а не WordPress-источники.

### Как это должно работать

**Сборщик.**
- Один постоянный процесс (systemd или supervisor), а не cron раз в минуту: нет наложений запусков.
- Параллельный опрос через `curl_multi`, 10–20 одновременных соединений. Все 150 фидов за 5–15 секунд.
- Условные запросы: хранить `ETag` и `Last-Modified` по каждому фиду. Большинство ответов будет 304 без тела.
- У каждого фида свой `next_check_at`. Активные источники опрашиваются раз в 1–2 минуты, вялые раз в 10–15 минут, интервал подстраивается под реальную частоту публикаций.
- Таймаут 10–15 секунд, экспоненциальный backoff по конкретному фиду. Один медленный источник никого не блокирует.
- Нагрузка: около 1,25 запроса в секунду, хватит 2 vCPU и 4 GB RAM, можно на существующем сервере.

**Админка (дашборд).**
- Управление списком источников: добавить, отключить, настроить интервал.
- Таблица здоровья фидов: последний успех, последняя ошибка, число подряд идущих ошибок, HTTP-код, время ответа. Нужна, чтобы молча умерший источник был виден сразу.
- Счётчики поступления статей по источникам за час и сутки, лента последних статей.
- Отдельный тип источника (`rss`, `html`, `social`) на случай сайтов без RSS: для них потребуется собственный парсер.

**Полный текст.**
- Если в RSS только анонс, полный текст добираем отдельной очередью (отдельный воркер), чтобы не тормозить опрос фидов. Это самая нагруженная и самая хрупкая часть системы, потому что вёрстка у каждого сайта своя.

**Новая БД (идея структуры).**
- `sources`: настройки фида и состояние опроса.
- `articles`: канонический URL, заголовок, текст, дата публикации в UTC, `source_id`, хеш для дедупликации, сырой RSS-элемент для возможности перепарсить.
- Дедупликация по `guid`, а если его нет или он нестабилен, по хешу нормализованного URL без UTM-меток.
- Правки статей после публикации: решить, перезаписываем или версионируем.
- Кодировка `utf8mb4` везде, чтобы армянский текст не искажался.
- Собственные ID через автоинкремент и `source_id` вместо схемы со смещениями `10B`.
- MySQL остаётся источником истины. Manticore строится как real-time индекс над этой БД.

**Миграция.**
- Архив с 2002 года остаётся в старых базах. Нужно решить, переносить ли его в новую структуру или держать рядом.
- Старый индекс Manticore работает параллельно, пока новый не докажет, что он не хуже.

## 4. Алерты клиентам без LIKE

### Как сейчас
Рассылка (email и Telegram) опирается на LIKE-запросы по ключевым словам клиента. Это дорого по нагрузке и неточно для армянского.

### Видение: Manticore Percolate (обратный поиск)
Обычный поиск отвечает на вопрос «какие статьи подходят под запрос». Алертам нужен обратный: «каким клиентам подходит эта новая статья». Для этого в Manticore есть percolate-таблицы.

1. Запросы всех клиентов (ключевые слова, фразы, исключения) хранятся как правила в percolate-таблице.
2. Каждая новая статья из RSS-сборщика один раз прогоняется через эту таблицу, и Manticore возвращает список сработавших правил.
3. Нет периодического сканирования базы по каждому клиенту: нагрузка пропорциональна числу новых статей, а не числу клиентов на объём архива.

### Как не потерять качество (и повысить его)

1. **Настроить токенизацию под армянский.** В percolate-таблице и в основном индексе использовать один и тот же набор настроек: правильный `charset_table` (приведение армянских заглавных букв U+0531–U+0556 к строчным U+0561–U+0586), инфиксный/префиксный индекс для подстрочных совпадений. Проверить, есть ли готовый армянский стеммер в используемой сборке Manticore, и если нет, закрывать морфологию списком форм (см. п. 2).
2. **Формы слов для каждого ключевого слова.** Нормализацию уже делаем через Grok (приведение к именительному падежу). Расширить: хранить для каждого ключа набор склонённых форм и добавлять их в правило через OR. Так покрываются падежи без шума от слишком широкой подстроки.
3. **Двухступенчатая проверка.**
   - Ступень 1 (Manticore): быстрый отбор кандидатов с высоким охватом.
   - Ступень 2 (PHP): проверка кандидата теми же правилами, по которым сейчас работает LIKE (границы слов, исключения, фразы). Это гарантия, что качество не хуже нынешнего, а ложные срабатывания отсекаются.
4. **Теневой режим перед переключением.** 1–2 недели гонять старую LIKE-логику и новую percolate-логику параллельно, сравнивать, что нашла каждая. Фиксировать расхождения: что новая пропустила (потеря охвата) и что добавила (новые находки или шум). Переключать клиентов, только когда потерь нет.
5. **Что можно улучшить сверх LIKE.** Ранжирование по релевантности, фразовые запросы с близостью слов, исключающие слова, дедупликация одной новости из нескольких источников в одно уведомление, группировка в дайджест вместо потока писем.

### Доставка
- Сработавшие правила попадают в таблицу очереди отправки: клиент, статья, канал (email или Telegram), статус, число попыток.
- Отдельный воркер отправляет сообщения с повторами и логом ошибок. Сборщик RSS и отправка независимы.
- Защита от дублей: уникальная пара «клиент, статья». Одну статью клиент не получит дважды.
- Ограничение частоты по клиенту, чтобы всплеск новостей не превращался в сотни писем.

### Что нужно проверить на тестовом стенде до внедрения
- Как percolate-таблица ведёт себя с инфиксными подстановками на армянском тексте (скорость и точность).
- Нужная точность склонённых форм на реальных запросах клиентов.
- Пропускная способность при пиковой нагрузке и числе активных правил.
