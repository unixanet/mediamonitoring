## 0. Роль и ответственность

## 1. Суть

Новая платформа пишется с нуля как «версия 3» на основе существующей: прежний код и его ошибки не переносятся, а все инструменты сохраняются и улучшаются. Старую систему (сайт и кабинет в репозитории Intranet) мы не переделываем, а заменяем.

Схема:

| Часть | Адрес | Где | Что |
|---|---|---|---|
| Сайт-витрина | `mediamonitoring.am` | отдельный сервер | маркетинг, цены, 3 языка (hy/ru/en). Логин ведёт в интранет. Репозиторий Intranet |
| Интранет (кабинет клиента) | `intranet.mediamonitoring.am` | OVH, тот же сервер, что и движок | инструменты, отчёты, кошелёк клиента |
| Движок сбора данных | (beta) | OVH | краулер, БД статей, Manticore, рассылки |
| Админка | в составе beta | OVH | управление пользователями, тарифами, кредитами; только английский интерфейс |
| API | после платформы | OVH | публичное API (в том числе для конкурентов); на нём строятся мобильная и десктопная версии |

### 2.1 Порядок и способ работы (владелец, 2026-11-04, вторая часть)

1. Приоритет сейчас: платформа, инструменты, вид, отчётность, анализ, тренды, экспорт данных. API, соцсети и всё внешнее в конце.
2. Инфраструктуру и БД создаём с нуля. Нагрузка большая: около 25 000 писем в месяц по email и заметно больше по Telegram. Схема должна быть идеальной: отчётность по отправкам и ошибкам хранится в БД, но БД не засоряется, старые данные регулярно удаляются, логи и отчёты не мешают пользователям.
3. Отчёты daily, weekly, monthly (и instant) собираются правильно, грамотно и красиво.
4. Сначала система работает на новой пустой БД: владелец тестирует, добавляет себя как пользователя, включает и отключает отчёты. В живую не выходим.
5. Когда всё работает идеально, владелец заново подключает текущую БД; из неё переносим клиентов, пароли, настройки. Интеграция в самом конце, чтобы ничего не запутать. Поэтому новая схема полностью документируется в GitHub.
6. Платежи, кошелёк, сброс пароля работают как сейчас: поведение существующих скриптов (`initiate_digest_payment`, `payment/*`, `login.php` сброс пароля) сохраняется, они работают идеально.
7. От владельца: новые данные Grok API и данные для БД. Схема лежит в папке `sql`, для импорта даётся команда для терминала (с паролями в команде).

## 3. Предлагаемая архитектура (предложения Claude, не утверждено)

### 3.1 Один слой логики, API-first
Вся бизнес-логика (поиск, тренды, анализ, кошелёк, права) живёт в одном слое, который вызывают и веб-интерфейс интранета, и публичное API. Отдельных «внутренних» запросов к БД из страниц нет. Это даёт готовое API без переписывания и одинаковые права и лимиты для всех клиентов.

API v1 (после платформы): версионирование в пути (`/v1/…`), ключи API с областями доступа (scopes) по тарифу, лимиты запросов и учёт расхода на ключ, идемпотентность для платных операций, спецификация OpenAPI, единый формат ошибок.

### 3.2 Права на инструменты (пункт 8)
- Таблицы: тарифы, инструменты, `plan_tools` (какой тариф что может), персональные выдачи `user_tool_grants` (вручную из админки, с датой окончания).
- Проверка права на каждый запрос в одном месте, а не в каждой странице.
- 15 текущих клиентов: флаг «полный доступ, старая цена» (все инструменты), лимиты применяются только к API.

### 3.3 Кошелёк (пункт 9, деньги)
- Журнал проводок (append-only), баланс как сумма проводок, а не поле, которое правят. Суммы целыми числами в минимальных единицах (без дробей), валюта AMD.
- Пополнение через Inecobank: подтверждение платежа сервер-сервер (как сейчас в `digest_success.php`), идемпотентность по номеру заказа, повторный колбэк не зачисляет дважды.
- Списание за запрос к Grok: сначала резерв, потом списание фактической стоимости; баланс не уходит в минус.
- Ручные корректировки только из админки, с записью автора и причины (журнал аудита).
- Лимит «X запросов в тариф» (включённая квота за месяц) и дальше расход с кошелька.
- Возвраты как обратные проводки, не удаление записей.

### 3.4 Grok на армянском (пункт 6)
- Один клиент к API Grok за интерфейсом: модель, таймауты, повторы, лимиты задаются в конфиге по типу задачи (тональность, резюме, тренды).
- Кэш результатов (хеш текста и типа задачи), чтобы не платить дважды за одну статью.
- Перед переключением на армянские промпты замерить качество на тестовой выборке армянских текстов (тональность, резюме) и сравнить со старым вариантом.
- Расход токенов пишется по пользователю и инструменту: это основа для кошелька и аналитики.

### 3.5 Рассылки и конфигурация (пункты 4, 5)
- Единая таблица очереди исходящих (`outbox`): клиент, статья, канал (email, Telegram, отчёт), статус, попытки. Совпадения из Manticore кладутся в очередь, отдельный воркер отправляет. Защита от дублей: уникальная пара «клиент, статья, канал».
- Почта за интерфейсом `Mailer`: отправка с отдельного сервера; шаблоны по языкам; обработка отказов; SPF, DKIM, DMARC для домена.
- Telegram за таким же интерфейсом.
- Одна конфигурация по окружениям. Секреты не коммитятся в репозиторий (правило CLAUDE.md) и читаются из окружения или игнорируемого файла.
- Отчёты и аналитика БД: страница состояния (объёмы, задержки, очередь, ошибки отправки, расход Grok).

### 3.6 Manticore (пункт 13)
- Real-time индекс над новой БД статей, настройки как в основном индексе (`min_infix_len='3'`).
- Алерты: сначала опрос новых статей по правилам клиентов, затем percolate (обратный поиск), если нагрузка потребует. План и проверки в [README.md](../README.md), раздел 4. Теневой режим со сравнением со старой LIKE-логикой.
- Запросы всегда с `LIMIT` и `OPTION max_matches`, ключевые слова через `escapeMatchQuery()`.

### 3.7 Соцсети (пункт 11)
Последний этап. Сейчас не обсуждаем и не делаем: сначала платформа, инструменты, отчётность. Вернёмся после запуска и тестов.

### 3.8 Вход с сайта в интранет (пункт 14)
Решить: регистрация и оплата остаются на сайте или переезжают в интранет, и как проходит вход (простая ссылка на `intranet.mediamonitoring.am/login` или единый вход с передачей сессии). Рекомендация: пока кнопка «Войти» ведёт на страницу входа интранета, регистрация и оплата живут в интранете (одна БД пользователей, одна система кошелька), сайт остаётся без БД.

### 3.9 База данных платформы (проект схемы, предложение)

Принципы:
- Отдельная БД `platform` (пользователи, тарифы, деньги, настройки, отправки, отчётность) рядом с БД статей `crawler`: тяжёлая запись отправок и логов не мешает чтению статей и наоборот.
- MySQL 8+, `utf8mb4`, время в UTC, суммы целыми числами. Версию MySQL и сервера уточним при получении доступа.
- Данные делятся на вечные (пользователи, тарифы, журнал кошелька, заказы), долгие (аудит) и короткие (очередь и журнал отправок, события, кэши, снимки трендов).
- Короткие объёмные таблицы партиционируются по месяцам (`RANGE` по дате создания). Удаление старого это `DROP PARTITION`: мгновенно, без нагрузки, таблицы не раздуваются. Внешние ключи на этих таблицах не ставим (ограничение партиционирования), целостность держит приложение.
- Перед удалением детали сворачиваются в дневные агрегаты (`stats_daily`), которые хранятся годами: отчётность по отправкам и ошибкам остаётся, а строки уходят.
- Очистка по расписанию одной задачей (`maint`), результат пишется в журнал запусков.

Группы таблиц:

| Группа | Таблицы | Хранение |
|---|---|---|
| Доступ | `users`, `password_resets`, `login_attempts` | вечно (попытки входа 30 дней) |
| Тарифы и права | `plans`, `tools`, `plan_tools`, `user_tool_grants`, `subscriptions` (история подписок) | вечно |
| Деньги | `orders`, `payment_events` (сырые ответы банка), `wallets`, `wallet_ledger` (журнал проводок), `wallet_holds`, `digest_subscriptions` | заказы и журнал вечно, события банка 5 лет |
| Настройки отчётов | `keywords`, `alert_rules` (правило: ключевое слово, канал email/Telegram, период instant/daily/weekly/monthly, источники, время, `next_run_at`), `crisis_rules` | вечно |
| Доставка | `outbox` (очередь и результат отправки), `outbox_items` (какие статьи в письме), `delivered` (защита от дублей: правило+статья), `delivery_errors` | outbox и items 90 дней, ошибки 180 дней, `delivered` 60 дней |
| Отчётность | `stats_daily` (отправки, ошибки, пользователи, расход Grok по дням), `keyword_stats_daily` (упоминания), `trend_snapshots` (срезы каждые 6 часов), `export_jobs` (экспорт в файл) | статистика годами, срезы 30 дней, экспорт 7 дней |
| ИИ | `ai_usage` (токены и стоимость по пользователю и инструменту), `ai_cache` (результат по хешу текста и задачи) | usage 13 месяцев, кэш по сроку |
| Админка и эксплуатация | `audit_log` (кто, что, над кем, до/после), `settings`, `job_runs` (запуски cron-задач) | аудит 24 месяца, запуски 30 дней |

Как рассылка устроена в БД:
1. Планировщик по индексу `alert_rules(next_run_at)` находит правила, срок которых пришёл, и считает следующий запуск (daily, weekly, monthly учитывают часовой пояс и день недели).
2. Для правила собираются новые статьи после курсора; из них убираются уже отправленные (`delivered`). Если есть что слать, создаётся запись в `outbox` с набором статей (`outbox_items`).
3. Воркер забирает записи пачками (`SELECT … FOR UPDATE SKIP LOCKED`), отправляет через канал, ставит статус `sent` или `failed` с кодом ошибки, повторяет с нарастающей паузой, после лимита попыток `failed` окончательно.
4. Лимиты канала: Telegram (не больше 1 сообщения в секунду на чат и общий лимит бота), email по лимитам почтового сервера. Очередь сглаживает всплески.
5. Любая отправка прослеживается: кто, какое правило, сколько статей, когда, результат, ошибка. По дням всё сворачивается в `stats_daily`.

Что изменится по сравнению со старой схемой: вместо двух почти одинаковых таблиц `report` и `report_telegram` одна `alert_rules`; даты следующего запуска хранятся одним полем, а не набором `next_run_daily/weekly/monthly`; подписка и тариф вынесены из `users` в `subscriptions`; `sent_articles` с длинными URL заменена компактной таблицей по ID статьи; сброс пароля через отдельную таблицу с сроком действия (для пользователя работает так же: временный пароль на почту); пароль хранится как bcrypt-хеш, как сейчас.

## 6. План работ (предложение)

Порядок: одна часть за раз, показать, получить отзыв, идти дальше.

1. Схема БД платформы (раздел 3.9) в `beta/sql/`, команда импорта. Миграция 15 текущих клиентов и их ключевых слов в самом конце, из текущей БД.
